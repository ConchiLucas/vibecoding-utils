# Aggregate Route Script Materialization Design

## Objective

Make every local aggregate deployment self-contained across computers. Before VibeDeploy executes an aggregate route, it must materialize exactly the child deployment routes referenced by that aggregate route's database-backed `start.sh`.

The fix must eliminate dependence on untracked `deploy/` files left by earlier individual deployments. It must work for mixed Java, Python, Go, Vue, and React project groups without hard-coding language-specific discovery.

## Confirmed Failure

English aggregate project `82`, route `149`, invokes seven child scripts. PostgreSQL contains all referenced child route scripts, but this computer has only the Go and React deployment directories on disk. The first missing file is:

```text
/Users/conchi/workforce/rob_english_word_workforce/deploy/backend/word_agent/build_project/start.sh
```

The current `prepareAggregateChildDeployScripts` implementation calls `detectGoReactComposeParts`, so it materializes only one Go backend and React frontends. It cannot prepare the Python `word-agent`, Java backend, or Vue frontend.

The English repository reports the complete `deploy/` directory as untracked local state. Another computer can therefore work at the same Git commit only because it has a different VibeDeploy database/version or deployment files retained from prior runs.

## Approaches Considered

### 1. Materialize explicitly referenced child routes — selected

Treat the selected aggregate route's database `start.sh` as its dependency manifest. Resolve each referenced child `start.sh` directory to an active local child route in the same project group, validate all dependencies, and materialize only those routes.

This matches actual execution, supports every language, and avoids unrelated routes.

### 2. Materialize every local route in the project group

This is simple but generates full, incremental, dependency-image, and unrelated scripts that the selected aggregate route does not use. It also makes ambiguous or broken unused routes block otherwise valid deployments.

### 3. Extend hard-coded language discovery

Adding Java, Python, and Vue branches would fix the current example but repeat the architectural flaw. New project structures or build modes would require more special cases and could fail silently again.

## Selected Architecture

The aggregate route's stored script is the source of truth for child dependencies.

The preparation pipeline has four isolated components:

1. **Reference parser:** extracts canonical child `start.sh` references from the aggregate script.
2. **Route resolver:** maps each referenced directory to one active local child route in the aggregate project's group.
3. **Preflight loader:** loads and validates every referenced route and all scripts before any database or filesystem write.
4. **Batch materializer:** stages and publishes the complete validated set, then permits aggregate execution.

No child service is started during preparation. Once preparation succeeds, the existing aggregate `start.sh` remains responsible for build/start ordering.

## Reference Parsing

The parser requires exactly one active, local `start.sh` for the selected aggregate route in `tb_project_script`; it does not trust a possibly stale disk copy. Missing or duplicate aggregate entry scripts fail preflight.

Supported child invocation format is the canonical format generated by VibeDeploy:

```sh
sh "$ROOT_DIR/deploy/backend/word_agent/build_project/start.sh"
bash "$ROOT_DIR/deploy/backend/example/local_full/start.sh" optional-arg
```

Rules:

- Accept `sh` and `bash` invocations rooted at `$ROOT_DIR`.
- Extract only paths ending in `/start.sh`.
- Preserve command order and de-duplicate repeated references by normalized directory.
- Ignore blank lines, comments, logging, variable setup, and commands that do not reference a child `start.sh`.
- If a non-comment line references `$ROOT_DIR/.../start.sh` but does not match supported syntax, fail preflight with the line number and content instead of silently skipping it.
- Reject absolute paths, `..` traversal, paths outside the aggregate project root, and a reference back to the aggregate route itself.
- Require at least one child reference.

The parser does not execute or generally interpret shell code.

## Route Resolution

For each normalized child script directory:

1. Convert the reference to an absolute directory under the aggregate project's `LocalProjectPath`.
2. Query active routes belonging to active non-aggregate projects in the same `group_id`.
3. Resolve each candidate's effective script path with the existing `resolveLocalScriptPath(route, childProject.LocalProjectPath)` behavior, then compare cleaned absolute paths exactly with the referenced directory. This preserves routes whose stored `local_script_path` is empty and currently falls back to project metadata.
4. Require `server_id = 0` because aggregate preparation is for local deployment.
5. Require exactly one match. Zero matches produce a missing-route error; multiple matches produce an ambiguity error.
6. Require an active non-remote `start.sh` script for the matched route.

Errors identify aggregate project/route, referenced path, and candidate child project/route IDs where applicable.

This resolution naturally selects both Python routes referenced by the English full deployment:

- `word-agent / build_project`
- `word-agent / local_compose_full`

It also selects the Java, Go, Vue, and React full routes without inspecting their language values.

## Batch Preflight and Materialization

The current single-route script preparation logic will be split into reusable load and publish phases.

### Load phase

For the aggregate route and all resolved dependencies:

- Load active, non-remote scripts from PostgreSQL.
- Validate every output filename remains inside its route's `local_script_path`.
- Apply existing frontend, Python, and shared-network normalizers in memory.
- Validate every Compose document.
- Confirm every referenced route includes `start.sh`.
- Detect duplicate target files with different content and fail as ambiguous.

No database content or local deployment file changes during this phase.

### Publish phase

After the complete dependency set passes preflight:

- Create required directories.
- Stage every file in its destination directory with final permissions.
- Open one database transaction and persist normalized content using optimistic `id + original content` conditions.
- While that transaction is still open, atomically rename staged files to their final targets.
- If any database update or filesystem rename fails, restore already-replaced files from exact per-file backups, remove newly created targets, and return an error so the open database transaction rolls back.
- Commit the database transaction only after every target file has been published successfully. If the transaction commit itself fails, restore the filesystem snapshot before returning the error.
- Clean temporary files on success and failure.

Only after publication completes does `ProcessDeployWithLog` execute the existing aggregate route.

Preflight failures occur before build or Compose execution and report the exact missing/ambiguous path.

## Compatibility

- Non-aggregate local deployments are unchanged.
- Remote deployments are unchanged.
- Existing Go/React aggregate routes continue to work through the new generic resolver.
- Full and incremental aggregate routes resolve independently from their selected stored scripts.
- Existing aggregate command order is unchanged.
- No schema migration is required.

The old Go/React-only preparation path will be removed from aggregate execution after equivalent tests pass. Project-type detection used while creating new projects remains unchanged.

## Testing Strategy

### Unit tests

- Parse canonical quoted `sh` and `bash` references.
- Preserve order and de-duplicate references.
- Ignore comments and unrelated commands.
- Reject unsupported child-reference syntax, traversal, absolute paths, self-reference, and empty dependency sets.
- Resolve exact child routes across Java, Python, Go, Vue, and React records.
- Reject missing and ambiguous route matches.
- Reject referenced routes without active `start.sh`.
- Preflight all dependencies before any write.
- Roll back staged/new/replaced files on a forced publish failure.
- Preserve the existing optimistic database-conflict behavior.

### Regression test

Build an in-memory English-style project group with:

- one aggregate full route;
- Python build-project and local-compose routes;
- Java full route;
- Go full route;
- Vue full route;
- two React full routes.

Run aggregate preparation and assert all seven referenced route directories receive their database-backed files while an unrelated incremental route remains untouched.

### Existing suites

- `go test ./service/system -count=1`
- focused `go test -race` for parser, resolver, materializer, and deployment guard
- `go vet ./service/system`
- shared-network shell tests and all seven Compose validations remain green

### Live acceptance

Before testing, record:

- English repository `deploy/` file paths and hashes;
- English-related containers, states, network modes, and published ports;
- Docker network inventory;
- current feature/base commit IDs.

Then execute English project `82`, route `149`, through VibeDeploy and verify:

- every referenced child file is materialized;
- the aggregate command reaches completion;
- expected English containers are running;
- every new container has persistent `HostConfig.NetworkMode=vibedeploy-shared` and only that network attachment;
- no project-specific Docker network is created;
- the configured access ports respond.

## Adoption and Rollback

Adoption requires every scoped unit, regression, race, vet, Compose, and live acceptance check to pass. On success, merge the feature branch into `main`, restart VibeDeploy from `main`, and repeat a bounded health/network verification.

If any aggregate-specific acceptance check fails:

1. Do not merge the aggregate-materialization commits.
2. Revert only aggregate-specific commits if already committed; retain the previously validated shared-network work.
3. Restore pre-existing English `deploy/` files from the recorded per-file snapshot and remove only files/directories created by this test.
4. Remove only English containers created by this test; restore pre-existing English container states and network modes.
5. Preserve middleware containers, `vibedeploy-shared`, images, volumes, bind-mounted data, and database records.
6. Re-run the pre-test inventory checks and report the failing acceptance step.

Rollback targets are always resolved from the recorded snapshot; no broad directory or Docker cleanup command is permitted.

## Out of Scope

- Tracking generated `deploy/` files in Git.
- Changing business source code.
- Changing aggregate build/start order.
- Redesigning project or route creation.
- Adding a route-dependency database table.
- Modifying remote deployment behavior.
